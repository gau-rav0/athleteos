# Samsung Health Data SDK 1.1.0 API audit

Inspected the locally supplied official AAR with JDK `jar` and `javap` before wiring. No SDK binary is committed. SDK BuildConfig reports version name `1.1.0` and code `1010004`. Namespace: `com.samsung.android.sdk.health.data`. The AAR BuildConfig reports SDK_VERSION_NAME `1.1.0` and SDK_VERSION_CODE `1010004`.

`HealthDataService.getStore(Context)` returns `HealthDataStore`. Its suspend APIs include `getGrantedPermissions(Set<Permission>)`, `requestPermissions(Set<Permission>, Activity)`, `readData(ReadDataRequest<T>)`, and `readChanges(ChangedDataRequest<T>)`. Permission construction is `Permission.of(DataType, AccessType.READ)`; no write permission or write API is used.

`DataTypes.HEART_RATE`, `SLEEP`, `EXERCISE`, `SKIN_TEMPERATURE`, `BLOOD_OXYGEN`, `BODY_COMPOSITION`, and `FLOORS_CLIMBED` expose `readDataRequestBuilder` (DualTimeBuilder) and `changedDataRequestBuilder`. `ENERGY_SCORE` exposes a LocalDateBuilder and the same change builder. Read builders support page size, page token, and ID filters. Changes support an instant change-time filter and page token. `DataResponse.dataList` and `pageToken` paginate responses. `Change.changeType` is UPSERT or DELETE; `upsertDataPoint`, `deleteDataUid`, and `changeTime` are public.

`HealthDataPoint` supplies `uid`, `clientDataId`, `clientVersion`, `dataSource.appId`, `dataSource.deviceId`, `startTime`, `endTime`, `zoneOffset`, `updateTime`, and typed field access. There is no public creation timestamp or separate end offset: those canonical fields remain null. DeviceManager.getDevice supplies source-device manufacturer/model/name/type where lookup succeeds. UID is preserved exactly, not replaced by clientDataId or a timestamp hash. Export datauuid correspondence still requires a private overlapping-device comparison; no alias is assumed.

`STEPS` and `ACTIVITY_SUMMARY` expose aggregate operations only, not raw Readable/ChangeReadable records. Their raw adapter status is UNSUPPORTED; Health Connect and the historical importer still preserve their raw observations independently. `USER_PROFILE` is readable but its UserDataPoint has no public UID, timestamps, or source metadata. It is UNSUPPORTED for this canonical raw pipeline rather than inventing an identity/time. No SDK RMSSD type is used.

The implementation uses a persisted change-time watermark, not an invented Samsung token API. Each request fixes its upper bound and starting watermark. The production client drains all SDK pages, sorts by changeTime and retains the latest event per UID before local transactional persistence; failed pages never advance a watermark. This avoids relying on undocumented page ordering or letting an earlier deletion override a later upsert. Completed windows replay a small boundary overlap on the next run. Snapshot and known-ID reads paginate fully and recheck permission. Only complete unbounded ID reads infer a missing Samsung UID; time-window absence alone never does. SDK failures do not imply deletions. Normal 72-hour and daily seven-day reconciliation remain controlled by the common sync engine.

Runtime Samsung Health availability, partner authorization, developer-mode setup, per-type support and physical reads remain device acceptance gates. Compiling against this binary does not certify them.

Platform missing, old version, or disabled/uninitialized states have explicit PLATFORM_MISSING, PLATFORM_UPDATE_REQUIRED and PLATFORM_UNAVAILABLE codes. Field serialization failures quarantine available metadata/fields with a fixed reason marker; they never print SDK exception messages or silently advance as accepted records.

JDK jdeps inspection also finds external Gson and AndroidX Data Binding references in this file-based AAR. The Samsung-enabled build supplies Gson and enables the matching Android Gradle Plugin Data Binding runtime/adapters; a files(AAR) dependency cannot resolve these transitively by itself.

Inspected public classes/interfaces: HealthDataService, HealthDataStore, DeviceManager, DataTypes, DataType.Readable/ChangeReadable and the eleven target type classes, ReadDataRequest.DualTimeBuilder/LocalDateBuilder/UserProfileBuilder, ChangedDataRequest.BasicBuilder, InstantTimeFilter, LocalDateFilter, IdFilter.Builder, DataResponse, HealthDataPoint, UserDataPoint, DataSource, Field, Change, ChangeType, Permission, AccessType, Device, HealthDataException and ErrorCode. Async futures were inspected but the implementation uses suspend APIs. Public sleep/exercise/sample entry getters are preserved as JSON, including nested sleep stages. Gson 2.11.0 and AGP-managed data-binding runtime dependencies are explicit because a local AAR has no dependency POM.

The SDK audit does not establish a change-retention duration; no guessed expiration threshold is used. Invalid persisted cursors trigger full reconciliation. SDK read failures retain the old cursor, and do not imply source deletion. Actual retention after extended downtime needs physical verification.

Official supporting references: [data types](https://developer.samsung.com/health/data/guide/features/data-types.html), [read changes](https://developer.samsung.com/health/data/guide/hello-sdk/read-changes.html), [permissions](https://developer.samsung.com/health/data/guide/hello-sdk/permission-request.html). Runtime version requirements come from the [official release notes](https://developer.samsung.com/health/data/release-note.html), not an invented AAR availability API.

Samsung time-window reads reconcile upserts only. The inspected time filter does not prove the exact start-time membership semantics used by Room for unfinished/spanning intervals, so absence from a range is not treated as deletion. Authoritative SDK DELETE events propagate tombstones. Cursor reset also compares known UIDs using unbounded ID-filter reads after all pages and permission rechecks succeed; failed/partial reads cannot delete records. Health Connect retains its documented complete start-window deletion reconciliation. This conservative distinction prevents a range-boundary omission from becoming a false Samsung tombstone.

SDK DELETE changeTime is preserved as the tombstone source_updated_at, while Room retains the original record payload/provenance/measurement times. This keeps cross-device conflict checks from rejecting a genuinely newer deletion solely because the old measurement was last edited earlier.
